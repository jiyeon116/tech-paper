# QECO-ADAPT2 Design

## 1. Objective

QECO-ADAPT2 evaluates whether a single QECO-family learner can vary its reward
and offloading gate according to the active-user density. The design keeps the
network and action space stable so comparisons isolate the effect of policy
selection rather than a larger agent architecture.

No empirical result is recorded in this document. Results must be generated by
the current code and retained outside version control.

## 2. Common Environment

The agent chooses one of the following actions for each user:

```text
0          local execution
1..N_EDGE  offload to the selected edge server
```

For an offloading action, the environment selects an AP cluster and AP-channel
resource. The observation therefore combines the QECO task and edge features
with an access score for each edge. Channel gain, channel occupancy, fronthaul
delay, and edge backlog affect transmission and processing outcomes without
expanding the agent's action set.

The default topology has three edge servers, six access points, four channels
per access point, and an AP-cluster size of three. Configuration values and all
environment-variable overrides are captured in each run's metadata.

## 3. Reward and Gate Variants

The registry exposes three primary QECO-family behaviors:

| Policy | Energy weight | Gate strength |
|---|---|---|
| `qeco` | QECO reward | no gate |
| `qeco-adapt-general` | active-user conditioned | fixed at 1 |
| `qeco-adaptive-gate` | active-user conditioned | active-user conditioned |

For a proposed edge action, the gate evaluates terminal energy state, target
edge backlog, task size, estimated local and transmission time, and the
edge-specific access score. If any rejection condition holds, the action is
converted to local execution. A proposed local action is unchanged.

The load-conditioned energy weight and gate strength are functions of the
active users in the current episode. Fixed-density experiments therefore use
constant values throughout a run, while random-density experiments update them
at every episode boundary.

## 4. Density-Regime Selector

At episode start, `qeco-adapt2` computes:

```text
density = active_users / number_of_edges
```

It then assigns one of three regimes:

```text
sparse   density < sparse threshold
general  sparse threshold <= density < dense threshold
dense    density >= dense threshold
```

Default thresholds are 50 and 350 active users per edge. The selected policy
for each regime is configurable through:

```text
QECO_ADAPT2_SPARSE_POLICY
QECO_ADAPT2_GENERAL_POLICY
QECO_ADAPT2_DENSE_POLICY
QECO_ADAPT2_SPARSE_MAX_USERS_PER_EDGE
QECO_ADAPT2_DENSE_MIN_USERS_PER_EDGE
```

The selector changes only the current energy-weight and gate modes. It does not
replace the agent network, replay memory, observation size, or action space.
Each run records the regime and resolved policy for reproducibility.

## 5. Density Schedules

Fixed mode activates the configured number of users in every episode. It is
appropriate for controlled policy comparisons and threshold sweeps.

Random mode creates the full agent pool once and samples an active-user count
for every episode. The active subset is either reproducibly randomized or
selected by prefix, depending on `QECO_DENSITY_SUBSET`. Inactive users receive
no arriving work for that episode. The same seeded schedule should be used for
paired comparisons across algorithms.

Important environment variables are:

```text
QECO_EXPERIMENT_FAMILY=adapt2
QECO_DENSITY_MODE=fixed|random
QECO_DENSITY_CHOICES=100,300,500,800,1200,1500
QECO_DENSITY_SUBSET=random|prefix
QECO_NUM_USERS=<agent-pool-size>
QECO_RANDOM_SEED=<seed>
QECO_RESULT_ROOT=<output-root>
```

## 6. Output Contract

Every completed run stores raw metric series, an experiment configuration, and
algorithm/runtime metadata. Random-density runs additionally store the active
user series, density schedule, and per-episode regime selection.

```text
results/adapt2/fixed_density/<algorithm>/run_*/
results/adapt2/random_density/<algorithm>/run_*/
results/adapt2/comparisons/fixed_density/<scenario>/
results/adapt2/comparisons/random_density/<scenario>/
```

The comparison tool produces overall and section summaries plus publication
figures. For random density it also produces per-regime summaries and an active
user timeseries. Existing `comparison_timeseries.csv` files can be rendered
again without rerunning training.

## 7. Evaluation Protocol

Use fixed-density runs first to verify aliases, gate behavior, and regime
boundaries. Then use paired random-density runs to test selection under a shared
episode schedule. Each reported claim should state:

- algorithms and exact configuration;
- active-user schedule and seed set;
- number of completed episodes per run;
- mean and dispersion across independently trained seeds;
- the metric direction and effect-size threshold;
- incomplete, timed-out, or excluded runs.

Single-seed comparisons are diagnostic and must not be presented as statistical
evidence. If a campaign has missing cells, analyze complete strata separately
and rerun a preregistered complete campaign for confirmatory conclusions.

## 8. Reproducibility Checks

Before interpreting results:

1. Run the unit tests and syntax checks.
2. Confirm CPU/GPU selection and TensorFlow session mode in runtime metadata.
3. Confirm that every raw metric has the requested episode count and finite
   values.
4. Verify that paired algorithms used the same seed and density schedule.
5. Check log exit status and reject partial runs from completed-run summaries.
6. Record checksums for `results/**` and `logs/**` with the artifact manifest.

These checks establish execution integrity; they do not replace statistical
validation of the research hypothesis.
